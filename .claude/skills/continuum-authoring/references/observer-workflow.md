# Continuum authoring: optional live observation and advice

Part of the [continuum-authoring skill](../SKILL.md). Strategic direction: [Vision V5](https://github.com/avlon-technologies/continuum-architecture/blob/main/VISION-V5.md). Existing normative semantics and authority rules retain precedence.

## 10. Observer workflow

Observation is an **optional** mode, for complex, prolonged or high-risk development where a timely independent challenge may matter. The default is to learn the architecture after development, or since the last checkpoint ([`architectural-learning.md`](architectural-learning.md)). The two are complementary: an Observer's record is an input to that recovery, never a substitute for it. Observation does not reliably produce better software or models. In the experiments it helped where a challenge landed before delivery, which needs a developer that works in more than one commit.

The developer owns application implementation, tests and reversible choices; the Architect owns routine architecture artifact authorship within applicable authority. Neither supervises the other. Advice is not permission. Do not gate reversible work or require check-ins, consultation, a complete model, or a development package before implementation. A capable developer may complete the entire implementation without consulting you.

### Start and observe

- Establish shared vision, known constraints, existing model and lifecycle status, accessible evidence, write ownership and observation mode. Use only authorized access; never modify application code or disclose repository content without authority.
- Prefer concurrent observation if the runtime actually supports it. Otherwise inspect stable snapshots at meaningful boundaries (working slice, consequential change, handoff). Do not claim live observation when unavailable, assume shared context, poll incessantly, or wait on developer messages. If no evidence is available, record the gap and resume when evidence is supplied.
- **Keep an explicit checkpoint.** It is the `evidence.json` anchor: `anchored.commit` is the implementation revision the model was last reconciled against. Declare `subject.surface.include` over the whole implementation, tests included, so that `continuum evidence check --anchored-at <rev>` names every file modified or added since then, and every citation whose code moved. That list is the work; a notification or a passing test run is not observation. Anchor (`evidence refresh`) only in a clean LF checkout of the examined revision, never over uncommitted edits. A missing or divergent checkpoint: the `continuum` skill's repository-history reference.
- **Observe in batches of related commits.** Load what is understood (scoped model queries, the learning record); read the commit messages, the listed diffs, new boundary files in full, changed tests, and callers of a changed seam. Record what changed, why (stated rationale with its source, or labelled inference), and the consequence for components, state ownership, boundaries, contracts, constraints and failure modes. Depth follows consequence. Unmoved code is not re-read by default, but unchanged bytes are not unchanged meaning: when a batch adds a caller, dependency, responsibility, trust boundary or constraint, examine the existing code whose role it changes.
- **Validate before modelling.** A behaviour someone states (a notice, a commit body, a README) is *declared* until code you read (*implemented*, cited `path:line`) or a test or run you can name (*verified*) supports it. Where the code does less than the claim, model what it does and raise the gap. A scenario verifies only what its steps observe.
- **Keep a learning record** beside the model (for example `continuum/OBSERVATIONS.md`), with one entry per batch: the revision range; a disposition for every changed implementation file (read, diff, or not architectural and why); assertions and their status; decisions with the alternative they replaced, abandoned designs included; and phrases the batch superseded. Then advance the checkpoint. Record unavailable evidence.

### Maintain architectural intelligence

Keep intended (accepted commitments), observed (implementation facts), proposed (not adopted), unknown and conflict distinct. Carry the kind in the construct, not only in prose: a `requirement` for intended; `satisfies:` plus a citation for implemented; a `test` that `verifies:` the requirement and the realizing element for verified; `service`, `api`/`operation` and `invokes:` for seams and their contracts. Observed is not accepted intent. Implementation evidence can establish realization, not automatically a business obligation or approval. Preserve prior rationale and alternatives; do not weaken a rule to make a check pass.

Incrementally author ADL, BDL, technology bindings, decisions and applicable principles where they carry consequential knowledge. Use existing locations and semantic tools; load the relevant artifact and lifecycle references. Update ordinary draft authored files where allowed, using the appropriate change mechanism; for adopted packages maintain proposals and evidence beside the authoritative state, never edit adopted files or perform human-only lifecycle acts. A model that is partial but accurate is preferable to invented completeness. Compile touched artifacts using available tooling; report actual results and NOT CHECKED where unavailable.

### Advise and intervene

Answer developer- or human-initiated questions from current evidence, scoped model queries and accepted intent. Distinguish facts, recommendations and unknowns; state model lag. Resume observation after answering. Do not require an answer or acknowledgment to continue.

Interrupt selectively when evidence indicates a material conflict with accepted intent, security or trust boundary, data integrity, costly irreversible decision, or missing consequential commitment that cannot safely be deferred. Give the evidence, impact, smallest actionable suggestion and accountable owner. Respect existing binding constraints and escalate genuine authority questions to the human. Batch nonurgent observations; do not challenge routine implementation details or request speculative approvals. Never silently absorb a contradiction; the developer corrects code or the authorized party resolves intent.

### Reconcile and hand off

At meaningful delivery boundaries, inspect the latest available stable revision and reconcile observed implementation against intended architecture. A closeout shows the record covers every change to the pinned revision (`evidence check --anchored-at`: verified, nothing touched); traces each consequential vision item to the model or a gap; runs the `recover-architecture` semantic-reconstruction checks and adversarial pass over what changed; re-runs cited verification from a clean checkout; rewrites the handoff to the final state; and, when the model will be relied on, ends with one fresh independent review given the material, not your conclusions. Where a build relies on the model, prefer a fresh Architect to recover it at closeout, using your record as an input (`architectural-learning.md` §2), so that conclusions inherited from earlier batches are re-established in the final code. Update permitted artifacts and proposals; compile relevant models, run appropriate bounded checks when warranted, and state the exact scope and result. A compile is not implementation verification; matching code is not conformance. Preserve conflicts and unverified claims. Do not require exhaustive package production or certification unless explicitly requested or required by existing policy.

Record a concise durable outcome in the existing intent/handoff or proposal record, respecting adopted paths: observed revision and scope, changes captured, evidence and checks, outstanding conflicts and unknowns, model freshness and observation gaps, and next useful action. Track effort and interruptions; stop work that adds no consequential understanding. Future agents resume from this record and current evidence. If the Architect is unavailable, reversible development may continue; report missed coverage at reconciliation.
